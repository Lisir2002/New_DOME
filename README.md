# SNG —— 三身份通用大模型架构

> **State-Navigated Generative（SNG）**：一套市面上没有的新大模型架构。核心主张是把大模型的「决策 / 知道 / 说话」三种能力**解耦为三个独立、可替换、可组合的模型身份**，用一套"池式黑板 + 电源管理 + 可验证状态"的骨架把它们组织起来。
>
> 关键区别：**本架构不绑定任何领域**——领域适配 = 下载对应插件文件 → 注册 → 即用，核心骨架不动、无需重训。
>
> 当前状态：**可运行原型**（首个验证基准：迷你文本游戏），36 项基础测试全部通过。

| 项目 | 状态 |
|---|---|
| 版本 | v0.3（机制验证原型） |
| 核心测试 | 36 项全通过（引擎 / WS / CRM / SVSL / 调度 / 总线 / Echo-er / 记忆追踪器 / 端到端链路） |
| 语言支持 | 中英双语（输入解析、状态记忆、输出） |
| 首个验证基准 | 迷你文本游戏（状态可验证、数据可自动生成） |

## 1. 项目简介

### 1.1 一句话定位

> **以"唯一主控制器（只调配）+ 可下载能力插件 + 独立 Echo-er（负责整个分析生成输出）"的通用三身份模型系统为骨架；用可编译规则记忆保证状态一致性的结构性可验证；用自验证循环保证"先验证再生成"；用黑板池式 + 电源管理 + 双层仲裁保证紧内存下的可扩展组合。**

### 1.2 三大身份

| 身份 | 规模 | 职责 | 常驻 |
|---|---|---|---|
| **主控制器** | 30~50MB | 理解 + 状态引擎判任务，**只调配、不说话** | ✅ 常驻（通用骨架） |
| **附属插件** | 各 ≤80MB | 各自持有领域能力，**默认关机、按需开机** | ❌ 按需加载（可下载） |
| **Echo-er** | ≤80MB | 读结论池，**组织优化总结输出** | ✅ 常驻（独立文件） |

### 1.3 硬约束

| 约束 | 要求 |
|---|---|
| 架构 | 通用三身份骨架，与领域无关 |
| 内存 | 主控制器 30~50MB；每个插件文件 ≤80MB；Echo-er 文件 ≤80MB |
| 激活 | 每个已加载模块内部**全激活**（稠密，无稀疏路由）；模块间按需动态调度 |
| 调度 | 控制器根据任务**动态调用**插件 |
| 领域适配 | 下载插件文件 → 注册 → 即用，无需重训核心（核心卖点） |
| 数据流程 | 插件结果**先验证再生成** |
| 电源管理 | 插件默认关机（零内存 / 零算力 / 零延迟），仲裁放行才开机 |
| 消息总线 | 主模型 →【指令池】→ 插件 →【结论池】→ Echo-er（黑板架构） |

## 2. 设计理念

### 2.1 核心命题

> **把"决策 / 知道 / 说话"解耦为三个独立、可替换、可组合的模型身份。**

- **谁决策** → 主控制器（理解 + 状态引擎 + 调度）
- **谁知道** → 附属插件（领域能力）
- **谁说话** → Echo-er（生成输出）

### 2.2 为什么三者分离是研究级亮点

1. **小控制器是稀缺品**：编排调度通常是大模型专利，30~50MB 专训调度模型是研究空白。
2. **插件可独立替换 / 升级**：加能力 = 加文件，能力阶梯天然成立；领域适配 = 下载插件文件即注册即用，核心骨架不动。
3. **Echo-er 分离生成**：生成质量（双语、叙事风格、角色语气）可独立强化，不被控制器 / 插件训练牵制。
4. **有状态调度**：控制器基于内置状态引擎调配，调度决策可验证，优于 LLM agent 的无根基工具调用。
5. **组合单调性（N+1≥N）**：加插件应让系统更强，是贯穿的核心命题。

### 2.3 为什么首个验证基准选文本游戏

不是定位，而是**证明机制最有利的场景**：

- 计算本质是显式、可验证的世界状态 + 自然语言动作理解 + 生成，能最直接检验「状态一致性 / 调度正确性 / 先验证再生成」。
- 状态迁移可观测、可自动生成（TextWorld 式引擎）→ 从零训练数据可解。
- 领域窄 → 各身份模型小、目标明确 → 从零训练现实可行。
- 机制验证通过后，其余领域**只换插件（下载即用），架构不变**。

## 3. 架构总览

### 3.1 数据流（黑板池式 + 电源管理）

```
用户输入
   │
   ▼
① 主控制器 (30~50MB) ──────── 常驻（通用骨架），理解 + 状态引擎判任务，只调配
   │  写【指令池】
   ▼
【指令池】────────────── 集中仲裁 → 插件开机 / 关机名单（预算硬约束）
   │  插件自判断器（纯规则）双重校验，防主模型分配错误
   ▼
② 插件 (各 ≤80MB) ──────── 通用能力插件 + 领域插件（可下载）
   │  默认关机；被放行的才开机处理
   │  结果有条理写【结论池】
   ▼
【结论池】── 验证器（内置）校验 ──▶ 通知 Echo-er
   │
   ▼
③ Echo-er (≤80MB) ────── 读结论池，处理优化总结，输出
   │
   ▼
最终输出
```

### 3.2 一回合时序

```
输入 ──► 控制器推理（状态读取 + 规则查询 + 调度决策 + 状态更新）
      ──► 写【指令池】→ 集中仲裁放行插件 → 插件自判断器双重校验
      ──► 被放行插件开机处理，写【结论池】
      ──► 验证器校验（先验证再生成）→ 通知 Echo-er
      ──► Echo-er 读结论池，输出最终回复
```

## 4. 核心机制详解

### 4.1 主控制器（唯一主模型，30~50MB）—— 新架构的心脏

**职责**：读入输入 → 结合状态 → 输出调度决策 + 状态更新。它是一个**带持久可验证状态的计算模型**（不是"LLM 随手选插件"）。

**内部组成（统一前向计算图）**：

| 组件 | 作用 |
|---|---|
| 编码器 | 小型双语 Transformer，把输入 token 编码为上下文 `h_t` |
| WS 状态读写层（§4.2） | 持久状态矩阵 `S ∈ R^{128×128}`，跨回合读写 |
| CRM 规则记忆层（§4.3） | 规则表：训练时可微、推理时编译为 DFA |
| SVSL 验证循环头（§4.4） | 计算图内的验证循环 |
| 调度头（§4.5） | 从 `h_t` + 状态读取生成调度决策 |

**主控制器前向（每回合）**：

```
x_t ──► Encoder ──► h_t
        ├──► WS Read ──► r ──► 与 h_t 融合 ─► h'_t ─► Dispatch head ─► d_t
        ├──► CRM query(h'_t + 状态模式) ──► 规则约束 / 迁移候选
        ├──► WS Write：生成状态更新候选 Δ
        └──► SVSL 循环（≤K 次）：
                s' = apply(S, Δ)
                v  = Verify(s', CRM 规则, 一致性检查)
                通过 → S := s'；失败 → Δ = Correct(Δ, 失败原因)
                仍失败 → 保留 S + 告警
输出：d_t + S_t + 验证结果
```

要点：

- 调度决策与状态管理是**同一前向的一部分** → 端到端可训练。
- 控制器**不直接产出最终叙述**——那是 Echo-er 的职责。

### 4.2 WS 状态读写层（State Workspace）

**结构**：持久状态矩阵 `S ∈ R^{128×128}`。每个槽 = **槽键**（可寻址表示）+ **槽值**（内容向量）。

- **类型化槽**：领域 schema 绑定固定槽位（如 `flag.door_locked → 槽#5`），语义固定。
- **自由槽**：无固定语义，content-addressable，模型自定存什么。

**读取（content-based）**：

```
α = softmax(q·K/√d)，r = Σ αᵢVᵢ
```

多查询头并行做**关系读取**（如"位置在 X 且背包有 Y"）。

**写入（混合寻址）**：

| 槽类型 | 寻址方式 | 优点 |
|---|---|---|
| 类型化槽 | **语义固定直写**（schema 直接映射槽位，无需学寻址） | 可精确验证 |
| 自由槽 | **content-based 软寻址**（写查询打分所有槽，软写或 Gumbel 稀疏写） | 灵活自组织 |

**更新操作（受控枚举，验证器可精确检查）**：`set / add / append / remove / clear`，由动作类型决定。

**与 KV cache 的本质区别**：

- KV cache 是**输入缓存**；WS 的 `S` 是**有语义、可读写的模型状态**。
- `S` 跨回合保留；读取 `r` 影响决策（读），决策生成 `Δ` 更新状态（写），形成闭环。

### 4.3 CRM 可编译规则记忆层（Compilable Rule Memory）

**结构**：规则表 `{ (状态模式, 动作模式, 迁移) }`，每条规则 = 三个可微嵌入 `E_pattern / E_action / E_transition`。

**可微索引学习（训练时）**：

```
查询 q = f(状态特征, 动作特征)
α = softmax(q·E_rule/√d)   # 在规则上软注意力
稀疏正则逼向单一匹配
L_match = CE(α, 引擎标注真值规则)
学成后 softmax 收敛到确定性 argmax
```

**编译为 DFA（推理 / 加载时）**：

- 软匹配硬编码（argmax），构造迁移表 `(状态模式, 动作) → 迁移`。
- 推理时查表 **O(1) 确定性迁移** → **一致性是结构性保证**。

**编译可靠性**（防止错误固化）：

| 机制 | 做法 |
|---|---|
| 编译门槛 | 匹配置信不足的规则**不编译**（留软记忆），避免错误固化 |
| 冲突检测 | 同一 `(状态, 动作)` 出不同迁移 → 报冲突，按 schema 优先级消解 |
| 覆盖补全 | DFA 未覆盖的 `(状态, 动作)` → 视为不合法动作，交验证器拒绝 |

**与 SVSL 衔接**：训练时 SVSL 用软 CRM 打分；推理时用编译 DFA 做确定性检查（`s'` 是否可达）。

### 4.4 SVSL 自验证循环头（Self-Verification State Loop）

**循环（≤K 次）**：

```
候选更新 s' → 验证打分 v = Verify(s', CRM 规则, 一致性/冲突检查)
   ├─ 通过 → 接受
   └─ 失败 → 用修正头产出修正 Δ 重试
        └─ K 次仍失败 → 保留旧状态 + 告警
```

**两个子组件**：

- **验证打分器**：小判别头（`h_t + s' + 规则约束` → 通过概率），或直接用 CRM DFA 的确定性检查。
- **修正头**：小回归 / 生成头，`(h_t, s', 失败原因) → 修正后的更新`。

**为什么在计算图内**：验证是训练时的计算结构（损失含"状态更新必须通过验证"），模型学会主动提出一致更新；它**不是部署后的安全过滤器**。

**先验证再生成**：对插件返回的分析 / 状态更新同样先验证再放行给 Echo-er。

### 4.5 调度头（Dispatch Head）

从上下文 `h_t` + 状态读取 `r` 生成调度决策：

```
d_t = ( task_types[]      # 多意图：有序列表，首位主意图
      , candidate_plugins # 候选插件（本任务该开机谁）
      , complexity        # 复杂度估计（影响仲裁阈值）
      )
```

训练时**直接监督引擎真值插件集合**（多标签 BCE），因此控制器学会的是"按需唤醒谁"的调度技能，而非停留在任务类型层面。

### 4.6 池式黑板 + 电源管理 + 双层仲裁

**池式黑板**：

| 池 | 生产者 → 消费者 |
|---|---|
| 指令池 | 主模型写 `DispatchRequest` → 仲裁器读 + 插件探针读（纯规则匹配） |
| 结论池 | 开机插件写 `AnalysisResult` → 验证器校验后生成 `GenerationRequest` 通知 Echo-er |

**电源管理（插件三态生命周期）**：

| 状态 | 含义 | 成本 |
|---|---|---|
| 关机 OFF（默认） | 不加载、不参与任何预算式子 | 零内存 / 零算力 / 零延迟 |
| 唤醒 WAKE | 被仲裁放行 → 加载处理 | 按成本卡计 |
| 探针 PROBE | 纯规则匹配的监听 | 成本 ≈ 0 |

**按需开机、用完即停**：每个任务开始时仲裁放行该任务需要的插件，结束后关闭不需要的插件。实测中：聊天轮只开机 `chat`（11.5MB），游戏轮只开机 `domain + memory`（16MB）。

**开机决策（双层校验）**：

```
开机 = 集中仲裁（主推） + 插件自判断器（纠错）
  · 仲裁器点名 → 插件判断器确认   —— 防误唤醒
  · 仲裁器漏派 → 插件判断器强相关，主动请求开机 —— 防漏派
```

## 5. 性能调度设计（三层）

### 5.1 三层总览

| 层 | 问题 | 内容 |
|---|---|---|
| 第 1 层 调度决策 | 选什么 | 控制器判定任务、选插件子集 + 顺序 + 参数 |
| 第 2 层 执行编排 | 怎么执行 | 执行图 DAG、并行、验证插入、降级兜底 |
| 第 3 层 资源调度 | 花多少资源 | 内存 / 延迟预算、能力阶梯自适应、带约束选择 |

先决条件：**插件注册表**，每插件一张**四维成本卡**。

### 5.2 第 1 层：调度决策

- 输入：用户输入 + 状态快照 + 当前目标；输出：调度计划（有序插件子集 + 参数 + 优先级）。
- 决策形态：生成式 / 分类式 / **混合式（先分类任务类型，再小步生成细节，推荐）**。
- 训练：引擎 rollouts 自动标注"最优调度"→ SFT，稳定后上 RL（调度 → 目标达成 → reward）。
- 评测：**调度正确率**（选中插件是否最优，引擎给 ground truth）。

### 5.3 第 2 层：执行编排

- 执行图（DAG）：可并行插件并发，有依赖插件串行。
- 验证插入：默认每插件结果**先验证再放行**；高精度插件可跳过校验。
- 降级：插件超时 / 低置信 → 跳过 + 控制器兜底，不阻塞回合。
- 运行时：轻量编排引擎（调度代码，非模型）。

### 5.4 第 3 层：资源调度（核心）

**四维成本卡**：

```
CARD(p) = ( g[p][τ]   # 能力增益：任务类型相关（增益矩阵，非标量）
          , mem[p]    # 内存成本
          , lat[p]    # 延迟成本
          , acc[p]    # 精度（决定能否跳过验证）
          )
```

**内存预算模型**：

```
MEM_peak = MEM_常驻(主模型 + 仲裁/探针 + Echo-er) + Σ_{开机 p} mem[p]
约束：MEM_peak ≤ MEM_BUDGET
```

- **关机插件不进入式子**（零占用，比 LRU 缓存更彻底）。
- 工程含义：**"同一时刻开机几个插件"是硬指标**，由仲裁与预算共同决定。

**延迟预算模型**：

```
LAT_turn = t_ctl(决策) + Σ并行波(插件) + t_ver(验证) + L × t_per_token(Echo-er)
```

- 控制杠杆：输出长度上限 `L`、插件并行波、高精度插件跳过验证。

**能力阶梯自适应**（"组合数量决定强弱"的运行时实现）：

| 档位 | 开机 | 场景 |
|---|---|---|
| L0 简单 | 主模型 + Echo-er | 看地图、打招呼 |
| L1 中等 | + 状态引擎 + 文字理解 | 开箱子、拿物品 |
| L2 复杂 | + 记忆 + 任务划分 + 领域知识 | 解谜、多目标 |

- 任务越复杂，仲裁阈值越低（放行更多插件开机）；简单任务阈值高（少开机）。
- 阶梯是**候选集**而非死档，最终由仲裁 + 预算分配收敛。

**预算分配算法（带约束选择）**：

```
目标：max Σ_{p∈S} g[p][τ]
约束：Σ_{p∈S} mem[p] ≤ MEM_BUDGET
      Σ并行波 lat ≤ LAT_BUDGET
```

- 插件数小（~5~10）→ **0/1 背包精确 DP 可解**，无需近似。
- 备选：按增益密度 `g/mem` 贪心取前 K。
- 增益带不确定性：期望增益（开发）/ 上置信界（探索），随部署数据收敛。

**运行时自学习**：每回合回填真实结果（任务成败、实际内存 / 延迟、插件使用）→ 在线更新 `g` 估计 → 成本卡自适应部署负载，调度器自优化。

**资源调度评测**：

- 资源利用率（难任务接近预算、易任务低开销）
- 性价比：每单位内存 / 延迟的任务成功率增益
- 阶梯单调性：`L1 ≥ L0`、`L2 ≥ L1`（组合单调性在阶梯上的具体化）
- Pareto 权衡曲线：任务成功率 vs 延迟，自适应调度器应贴合前沿

## 6. 插件体系与市场

### 6.1 插件分类

| 类型 | 说明 | 例子 |
|---|---|---|
| 通用能力插件 | 与领域无关，随骨架发布 | 记忆、文字理解、任务划分、双语转换 |
| 领域插件 | 按需从插件市场下载 | 文本游戏包、法律咨询包、医疗问答包、代码分析包 |

### 6.2 插件清单（Manifest）

每个插件文件自带 `manifest.json`，声明身份、体积、能力与成本：

```json
  "version": "1.0.0",
  "category": "domain",

  "format": "lbnt_ternary",
  "cost_card": {

    "latency_ms": {"p50": 120, "p95": 200},
    "accuracy": 0.91,
    "gain_matrix": {"reasoning.puzzle": 0.35, "action": 0.20, "retrieval.kb": 0.15}
  },
  "capabilities": ["world_rules", "puzzle_solving"],
  "judge": {"rules_version": "1", "confirm": [...], "veto": [...]},
  "task_types": {"action": ["loco", "obj", "combat", "dialog"], "reason": ["puzzle"]},
  "dependencies": [{"id": "sng.text_understanding", "min_version": "1.0.0"}],

  "signature": "sha256:..."

```

### 6.3 注册流程（下载即用的生命周期）

```
下载 → 签名/依赖校验 → 安装（入插件目录） → 注册（manifest 入表）
     → 成本卡入表 → judge 规则编译 → 词表扩展（task_types 并入） → 即用
```

- 依赖解析：缺运行时 / 缺依赖插件 → 提示一并下载或拒绝安装。
- 版本兼容：semver；`protocol_version` 必须兼容；单插件可热更新 / 回滚，骨架不动。

### 6.4 注册表与市场

- **PluginRegistry**：协议版本、已注册插件、运行时（LBNT 版本 / 内存预算 / 最大并发唤醒数）、任务词表（核心 + 领域扩展）、编译后的 judge 规则、运行时增益覆盖。
- **市场索引**：远程索引（摘要 + 大小 + 版本 + 下载地址 + 签名）；离线安装（manifest + 模型文件直接放入插件目录即注册）；签名校验与权限声明保障信任与安全。

## 7. 模型间接口协议

**原则**：不传自由文本、全结构化；消息头极轻（插件要快速分辨）；`task_id` 贯穿全流程；带可校验字段。序列化开发用 JSON（可读、易调试），交付用 CBOR / MessagePack（体积小、解析快）。

### 7.1 六类消息

| 消息 | 方向 | 关键字段 |
|---|---|---|
| DispatchRequest | 主模型 → 指令池 | `task_types[]`、`complexity`、`state_snapshot`、`candidate_plugins[]`、`goal` |
| WakeNotice / WakeRequest | 仲裁器 → 插件 / 插件自请求 | `reason`（双层校验标记）、`budget` |
| AnalysisResult | 插件 → 结论池 | `result_object`、`confidence`、**`claims[]`（原子断言）** |
| VerificationReport | 验证器 | `verdict`（pass / fail / correctable）、`issues`、`passed_to_echo` |
| GenerationRequest | → Echo-er | `scene`、`state`、`facts[]`、`style`、`language`、`max_tokens`（延迟控制杠杆） |
| ProbePing | 插件探针心跳 | `status`（off / probe_only）、`judge_rules_version` |

### 7.2 端到端示例（"打开那扇锁着的门"）

1. 主模型 → 指令池：`DispatchRequest{task_types:["action.obj"], parsed_action:{verb:"open", target:"door"}, state_snapshot:{flags:{door_locked:true}}}`
2. 仲裁器 → `WakeNotice{state_engine, text_understanding, domain_kb}`
3. text_understanding 探针：`task_types` 含 `action.obj` 命中能力映射 → 确认开机
4. 插件 → 结论池：`AnalysisResult{result_type:"parse", claims:[{type:"state_change", slot:"flags", op:"set", value:"door_open", if:{has_key:true}}]}`
5. 验证器：`VerificationReport{verdict:"pass"}`
6. 主模型 → Echo-er：`GenerationRequest{scene, state, facts, language:"zh", max_tokens:60}`
7. Echo-er 输出："你拧动门把，门锁应声而开。"

> 关键设计点：**`claims[]`（原子断言）是验证器的输入**——插件给出带前置条件的可校验断言（如 `if:{has_key:true}`），验证器据此判 pass / fail，"先验证再生成"在协议层落地。

## 8. 内存预算

| 组件 | 文件数 | 预算 |
|---|---|---|
| 主控制器（调度 + 状态引擎 + 验证器） | 1 个 | **30~50MB** |
| 附属插件 | 每能力 1 个 | **各 ≤80MB**（通常仅几 MB~几十 MB） |
| Echo-er | 1 个 | **≤80MB** |

- 精度路线沿用 **LBNT（低比特原生训练，1.58bit 三值 / INT4）**，让每个文件都薄。
- 一个完整部署 = 主控制器 + 选定插件 + Echo-er；插件按任务动态加载，能力阶梯 = 可组合的插件数量。

## 9. 训练方案

### 9.1 数据来源（引擎自动产出，几乎免人工）

```
样本 = (x_t, s_t, a_t, s_{t+1}, d*_t, rule*_t, slot_ops*_t)
  x_t 输入/观察文本     s_t / s_{t+1} 引擎真值状态（WS 监督）
  a_t 动作              d*_t 最优调度（引擎 rollout 标注）
  rule*_t 真值规则（动作合法表）      slot_ops*_t 槽更新（(s_t, s_{t+1}) 差异自动提取）
```

### 9.2 分阶段训练（渐进式）

| 阶段 | 内容 |
|---|---|
| 0 数据引擎 | 迷你引擎就绪，产出全部监督 |
| 1 单机制预训练 | WS（状态世界模型）、CRM（规则索引学习）、调度头（给定输入+状态 → 最优调度）各自独立学 |
| 2 身份分训 | 控制器把 WS + CRM + SVSL + 调度头连成完整前向训练；插件、Echo-er 各自独立训练 |
| 3 联合微调 | 完整回合 rollout，统一损失端到端对齐 |
| 4 课程学习 | 难度渐进：单步动作 → 多步记忆 → 解谜长程 |
| 5 强化 / 自学习 | 调度 RL（先 SFT 后 PPO）+ 运行时增益在线更新 |

### 9.3 统一损失目标

```
L_total = λ1·L_dispatch（调度 vs d*） + λ2·L_state（WS 读写 vs s*）
        + λ3·L_verify（更新必须通过验证） + λ4·L_crm（规则索引 vs rule*）
        + λ5·L_plugin（插件任务） + λ6·L_echo（生成） + λ7·L_sparsity（稀疏正则）
        + λ8·L_bilingual（跨语言一致：同一状态中英输出一致）
```

`λ` 随阶段调整：分训时各损失独立，联合时加权。

### 9.4 跨文件训练（插件是独立文件，不做跨文件反传）

- **交替训练（坐标下降）为主**：固定插件训控制器 ↔ 固定控制器训插件，迭代交替。
- 控制器内部（WS / CRM / SVSL / 调度头）本身是一个模型 → 端到端反传。
- 联合微调只在控制器内部做完整端到端；跨身份用交替 + 对接目标。

### 9.5 离散 / 不可微处理

| 部分 | 训练时 | 推理时 |
|---|---|---|
| 自由槽寻址 | Gumbel straight-through / 软写 | 软写 / 硬索引 |
| CRM 匹配 | 软 attention（可微） | 编译 DFA 硬匹配 |
| SVSL 循环 | 展开 K 次 + stop-gradient | DFA 确定性检查 |
| 调度多意图 | 多标签 softmax | argmax |

### 9.6 消融设计（证明每个机制必要）

| 消融 | 移除 | 预期影响 |
|---|---|---|
| -WS | 状态读写（用普通 KV） | 状态一致性崩 |
| -CRM | 规则记忆（无 DFA） | 长程 / 规则任务崩 |
| -SVSL | 验证循环 | 状态污染累积 |
| -调度头 | 随机 / 规则调度 | 调度正确率降 |
| -三身份 | 单一大模型 | 内存 / 可扩展崩 |
| -LBNT | 全精度 | 内存超 50MB |

## 10. 评测与基准

**数据来源**：英文用 TextWorld / Jericho / IF Archive 自动产出监督三元组；中文自建双语迷你引擎（中英动作模板共享状态机）。

**核心指标**：

- 状态一致性（20+ 回合 vs 引擎真值）
- **调度正确率**（控制器选中的插件是否是该任务最优）
- **组合单调性**（N+1 个插件的系统是否 ≥ N 个）
- 指令完成率、目标达成率；叙述连贯性；中英双语能力

**Baseline 对照**：

- 同尺寸 vanilla Transformer 微调
- Llama-3.2-1B + prompt + JSON 状态
- 单一大模型（无插件）
- 单模型含 Echo-er 功能（无三身份解耦）

## 11. 研究贡献定位

| 相关工作 | 区别 |
|---|---|
| 单一 LLM agent（大模型全包） | 决策 / 知道 / 说话耦合；本架构三身份解耦且各身份小 |
| MoE | 单 checkpoint 内 token 级路由；本架构是多文件部署级组合，模块间按任务调度 |
| Neural Module Networks | 按输入动态组合（VQA）；本架构按部署组合、可交付多文件、面向交互式状态建模 |
| Adapter / LoRA 叠加 | 本架构把组合做成"可交付文件 + 能力阶梯 + 单调性目标"的一等公民系统 |
| 黑板架构（Hearsay-II 等） | 本架构把黑板与**电源管理**结合：插件默认关机、仲裁放行才开机，为紧内存预算做硬保证 |
| 通用大模型 + 微调 / RAG / Adapter 换领域 | 换领域要重训或挂外部知识；本架构**领域适配 = 下载插件文件即注册即用**，核心骨架不动 |

**贡献表述**：以"唯一主控制器（只调配，内置状态引擎 + 验证器）+ 可下载能力插件 + 独立 Echo-er（负责整个分析生成输出）"的通用三身份模型系统，用 LBNT 低比特原生保证各文件内存，以可编译规则记忆 CRM 保证状态一致性的结构性可验证，以自验证状态循环 SVSL 保证先验证再生成，以黑板池式 + 电源管理 + 双层仲裁保证紧内存下的可扩展组合；**领域适配 = 下载插件即注册即用**，核心骨架与领域无关。

## 12. 风险与开放决策

### 12.1 主要风险

1. **小控制器调度能力不足**：30~50MB 可能难以胜任复杂调度——最大技术风险。缓解：插件做重活、控制器只做轻调度；调度数据由引擎 rollouts 高质量标注；必要时取 50MB 上限。
2. **组合单调性难保证**：N+1 模块互相干扰导致退化。缓解：接口协议 + 门控 / 归一化 + 单调性评测门槛。
3. **LBNT 训练稳定性**：三值原生训练收敛慢 / 不稳。缓解：课程训练、先在迷你引擎验证。
4. **CRM 离散结构难学**：缓解：课程式 + 引擎规则级标注 + 编译正确性评测。
5. **中文语料稀缺**：需自建双语迷你引擎 / 翻译对齐。
6. **三身份联合微调的一致性**：需消融验证分训 + 联合 vs 端到端。

### 12.2 开放决策（做成消融）

1. 控制器规模在 30~50MB 内的甜点；调度策略是"生成调度计划"还是"分类选插件"。
2. 插件接口协议字段粒度与序列化格式。
3. 验证器"先验证再生成" vs 事后抽查的配置。
4. LBNT：三值 vs INT4；各身份精度是否一致。
5. 组合单调性的实现机制（模块门控 / 组合归一化 / 插件专属头）。
6. 插件数量上限与"能力阶梯"的粒度。
7. task_type 词表粒度：两级是否够用、细类数目。
8. 规则库来源比例：手工 / 引擎自动导出 / 运行时调优。
9. 仲裁阈值与成本卡增益的联动方式。
10. 插件市场形态：集中市场索引 vs 去中心化分发。

## 13. 里程碑路线图

1. **迷你引擎 + 接口协议原型**：自写双语迷你引擎，先定"控制器 → 插件 → 验证器 → Echo-er"的接口协议与最小链路。
2. **单身份验证**：分别验证控制器调度、状态引擎（WS + CRM）、Echo-er 生成能否独立学出。
3. **三身份集成**：完整链路跑通，验证"加插件变强"（组合单调性）。
4. **内存达标**：LBNT 低比特原生 + 精简运行时，锁定 主 30~50MB / 插件与 Echo-er ≤80MB。
5. **研究收尾**：baseline 对照 + 消融 + 论文写作；追加第二个领域插件，验证"下载即用"的通用性。

## 16. 交互示例

### 游戏指令（走完整三身份链路）

```
> 去厨房

【分析】你位于厨房，此处物品有面包；大门锁着。动作「去厨房」可以执行：该房间可达。
【结果】状态更新已通过一致性验证，可以继续行动。
  · 动作=go 规则=move_valid 验证=通过 峰值内存=16.0MB
```

### 通用对话（域外兜底，同样走完整链路）

```
> 你是谁
【回复】我是 SNG 三身份模型系统：由主控制器统一调度，按需唤醒领域插件，再由 Echo-er 整理输出。…
  · 模式=chat 唤醒=['chat'] 峰值=11.5MB
```

**电源管理可观察**：聊天轮只开机 `chat`（11.5MB），游戏轮只开机 `domain + memory`（16MB）——不需要的插件确实不占用性能。
